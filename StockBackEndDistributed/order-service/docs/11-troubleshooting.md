## OrderBook 자료구조 설계

### 문제

실시간으로 주문이 계속 들어오는 환경에서는 가격 우선, 시간 우선 규칙을 만족하면서도 빠르게 주문을 조회하고 체결해야 했다.

처음에는 데이터베이스에서 매수·매도 주문을 조회하여 처리하는 방법을 고려했지만,<br> 새로운 주문이 들어올 때마다 최우선 호가를 조회하고 잔량을 갱신해야 하므로 조회 비용이 커지고 응답 속도가 느려질 수 있었다.<br> 특히 주문량이 많아질수록 동일한 데이터를 반복해서 조회해야 하는 문제가 있었다.

### 해결

이 문제를 해결하기 위해 종목별 OrderBook을 메모리에서 관리하도록 설계했다.

OrderBook 내부에서는 가격을 기준으로 PriceLevel을 관리하고, 같은 가격의 주문은 하나의 PriceLevel 안에서 FIFO 큐로 관리하도록 구현했다.

이 구조를 사용하면 가격 우선 원칙은 TreeMap이, 시간 우선 원칙은 Queue가 자연스럽게 보장되므로 별도의 정렬 과정 없이 최우선 주문을 빠르게 찾을 수 있었다.

### 결과

- 최우선 호가를 빠르게 조회할 수 있게 되었다.
- 같은 가격의 주문도 먼저 들어온 순서대로 체결할 수 있었다.
- 데이터베이스는 영속성만 담당하고, 실시간 매칭은 메모리에서 처리하도록 역할을 분리할 수 있었다.

## KIS 시세 연동 중단

### 문제

프로젝트 초반에는 실제 주식 시장과 비슷한 환경을 만들기 위해 KIS Open API를 이용한 시세 연동을 시도했다.

하지만 프로젝트 내부에서는 주문 체결을 기준으로 현재가를 생성하고 있었고, KIS는 실제 시장의 현재가를 제공하기 때문에 두 데이터가 서로 다른 값을 가지는 문제가 발생했다.

그 결과 차트, 현재가, 체결 내역이 서로 다른 기준을 사용하게 되었고, 사용자 입장에서도 일관성 없는 화면이 표시되었다.

### 원인

프로젝트 내부의 현재가는 내부 주문 체결 결과를 기준으로 계산된다.
반면 KIS는 실제 시장 데이터를 전달하므로 동일한 종목이라도 가격이 달라질 수 있다.
두 가지 기준을 동시에 사용하면 어느 값을 기준으로 차트와 호가를 표시해야 하는지 일관성을 유지하기 어려웠다.

### 해결

최종적으로 프로젝트에서는 외부 시세를 사용하지 않고, 내부 체결 결과만을 기준으로 현재가와 차트를 생성하는 방식으로 변경했다.


## 다양한 분봉 저장 구조 설계

### 문제

차트는 1분봉뿐만 아니라 3분봉, 5분봉, 10분봉, 30분봉, 1시간봉, 일봉 등 다양한 주기를 지원해야 했다.

처음에는 각 분봉을 모두 별도의 테이블로 저장하는 방법도 고려했지만, 분봉 종류가 늘어날수록 동일한 데이터를 여러 번 저장하게 되어 데이터베이스 용량과 관리 비용이 크게 증가하는 문제가 있었다.

반대로 1분봉만 저장할 경우에는 조회할 때마다 모든 분봉을 계산해야 하므로 조회 성능이 떨어질 수 있다는 문제도 있었다.

### 해결

여러 방식을 검토한 끝에 모든 분봉을 저장하는 대신 1분봉, 1시간봉, 일봉, 주봉, 월봉, 연봉만 데이터베이스에 저장하도록 설계했다.

3분봉, 5분봉, 10분봉, 30분봉은 저장하지 않고, 조회 시 1분봉 데이터를 필요한 단위로 그룹핑하여 생성하도록 구현했다.

### 결과

- 데이터베이스 저장 공간을 줄일 수 있었다.
- 관리해야 하는 Candle 테이블 수도 최소화할 수 있었다.
- 다양한 분봉을 지원하면서도 저장 비용과 조회 성능 사이의 균형을 맞출 수 있었다

## Candle 공통 인터페이스와 시간 타입 분리

### 문제
분봉, 시간봉, 일봉, 주봉 등 여러 종류의 Candle을 구현하면서 대부분의 필드와 동작이 동일하다는 것을 확인했다.

중복 코드를 줄이기 위해 공통 인터페이스를 도입했지만, 시간 정보를 표현하는 타입이 서로 달라 하나의 타입으로 통일하기 어려운 문제가 발생했다.


### 원인
분봉과 시간봉은 거래 시각까지 표현해야 하므로 LocalDateTime이 필요하지만, 일봉·주봉·월봉·연봉은 날짜 정보만 필요하기 때문에 LocalDate를 사용하는 것이 더 적합했다.

모든 Candle을 하나의 시간 타입으로 통일하려고 하면 불필요한 정보가 저장되거나 타입 불일치 문제가 발생했다.

### 해결

공통으로 사용할 수 있는 필드와 동작만 인터페이스로 추상화하고, 시간 타입은 각 Candle이 필요한 형태를 그대로 유지하도록 설계했다.

공통성을 유지하면서도 각 Candle의 특성을 살릴 수 있는 방향을 선택했다.

## 현재 Candle과 완료 Candle 저장 구조 분리

### 문제

현재 진행 중인 Candle은 체결이 발생할 때마다 시가, 고가, 저가, 종가, 거래량 등이 계속 변경된다.

이를 체결이 발생할 때마다 데이터베이스에 저장하거나 수정하면 불필요한 쓰기 작업이 반복되고, 실시간 처리 성능에도 영향을 줄 수 있었다.

또한 당일 일봉은 아직 완료되지 않았기 때문에 조회 시 매번 1분봉을 모두 계산해야 하는 문제도 있었다.

### 해결

현재 진행 중인 Candle은 Redis에서 관리하고, 시간이 지나 봉이 완성되는 시점에만 데이터베이스에 저장하도록 역할을 분리했다.

당일 일봉 역시 Redis에서 함께 관리하여 별도로 1분봉 전체를 조회하지 않아도 최신 값을 바로 조회할 수 있도록 설계했다.

이를 활용해 주봉, 월봉, 연봉도 당일 일봉 값을 기준으로 현재 고가와 저가를 계산하도록 구성했다.

### 결과

- 실시간 Candle 갱신 속도를 높일 수 있었다.
- 데이터베이스의 불필요한 쓰기 작업을 줄일 수 있었다.
- 현재 진행 중인 Candle과 완료된 Candle의 역할을 명확하게 분리할 수 있었다.

## Cache와 DB 조회 구간 중복

### 문제

최근 Candle 데이터는 Cache에 저장하고, 오래된 데이터는 데이터베이스에서 조회하도록 구성했다.

하지만 조회 범위가 Cache와 데이터베이스 구간을 동시에 포함하는 경우, Cache 데이터만 조회하면 일부 데이터가 누락되고, 두 데이터를 단순히 합치면 중복되는 문제가 발생했다.

### 해결

조회 요청이 들어오면 먼저 Cache와 데이터베이스의 조회 구간이 겹치는지 확인하도록 구현했다.

구간이 겹치는 경우에는 Cache와 DB를 단순히 병합하지 않고, 데이터 누락이 발생하지 않도록 데이터베이스를 기준으로 조회하도록 변경했다.

### 결과

- Cache와 데이터베이스를 함께 사용하는 환경에서도 데이터 누락을 방지할 수 있었다.
- 조회 결과의 일관성을 유지할 수 있었다.
- Cache와 DB를 혼합 사용하는 구조에서도 안정적으로 Candle 데이터를 제공할 수 있었다.
