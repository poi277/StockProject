## OrderBook 자료구조 설계

### 문제

실시간으로 주문이 계속 들어오는 환경에서는 가격 우선, 시간 우선 규칙을 만족하면서도 빠르게 주문을 조회하고 체결해야 했습니다.

처음에는 데이터베이스에서 매수·매도 주문을 조회하여 처리하는 방법을 고려했지만,<br> 새로운 주문이 들어올 때마다 최우선 호가를 조회하고 잔량을 갱신해야 하므로 조회 비용이 커지고 응답 속도가 느려질 수 있었다.<br> 특히 주문량이 많아질수록 동일한 데이터를 반복해서 조회해야 하는 문제가 있었습니다.

### 해결

이 문제를 해결하기 위해 종목별 OrderBook을 메모리에서 관리하도록 설계했습니다.

OrderBook 내부에서는 가격을 기준으로 PriceLevel을 관리하고, 같은 가격의 주문은 하나의 PriceLevel 안에서 FIFO 큐로 관리하도록 구현했습니다.

이 구조를 사용하면 가격 우선 원칙은 TreeMap이, 시간 우선 원칙은 Queue가 자연스럽게 보장되므로 별도의 정렬 과정 없이 최우선 주문을 빠르게 찾을 수 있었습니다.

### 결과

- 최우선 호가를 빠르게 조회할 수 있게 되었습니다.
- 같은 가격의 주문도 먼저 들어온 순서대로 체결할 수 있었습니다.
- 데이터베이스는 영속성만 담당하고, 실시간 매칭은 메모리에서 처리하도록 역할을 분리할 수 있었습니다.

## KIS 시세 연동 중단

### 문제

프로젝트 초반에는 실제 주식 시장과 비슷한 환경을 만들기 위해 KIS Open API를 이용한 시세 연동을 시도했습니다.

하지만 프로젝트 내부에서는 주문 체결을 기준으로 현재가를 생성하고 있었고, KIS는 실제 시장의 현재가를 제공하기 때문에 두 데이터가 서로 다른 값을 가지는 문제가 발생했습니다.

그 결과 차트, 현재가, 체결 내역이 서로 다른 기준을 사용하게 되었고, 사용자 입장에서도 일관성 없는 화면이 표시되었습니다.

### 원인

프로젝트 내부의 현재가는 내부 주문 체결 결과를 기준으로 계산됩니다.
반면 KIS는 실제 시장 데이터를 전달하므로 동일한 종목이라도 가격이 달라질 수 있습니다.
두 가지 기준을 동시에 사용하면 어느 값을 기준으로 차트와 호가를 표시해야 하는지 일관성을 유지하기 어려웠습니다.

### 해결

최종적으로 프로젝트에서는 외부 시세를 사용하지 않고, 내부 체결 결과만을 기준으로 현재가와 차트를 생성하는 방식으로 변경했습니다.


## 다양한 분봉 저장 구조 설계

### 문제

차트는 1분봉뿐만 아니라 3분봉, 5분봉, 10분봉, 30분봉, 1시간봉, 일봉 등 다양한 주기를 지원해야 했습니다.

처음에는 각 분봉을 모두 별도의 테이블로 저장하는 방법도 고려했지만, 분봉 종류가 늘어날수록 동일한 데이터를 여러 번 저장하게 되어 데이터베이스 용량과 관리 비용이 크게 증가하는 문제가 있었습니다.

반대로 1분봉만 저장할 경우에는 조회할 때마다 모든 분봉을 계산해야 하므로 조회 성능이 떨어질 수 있다는 문제도 있었습니다.

### 해결

여러 방식을 검토한 끝에 모든 분봉을 저장하는 대신 1분봉, 1시간봉, 일봉, 주봉, 월봉, 연봉만 데이터베이스에 저장하도록 설계했습니다.

3분봉, 5분봉, 10분봉, 30분봉은 저장하지 않고, 조회 시 1분봉 데이터를 필요한 단위로 그룹핑하여 생성하도록 구현했습니다.

### 결과

- 데이터베이스 저장 공간을 줄일 수 있었습니다.
- 관리해야 하는 Candle 테이블 수도 최소화할 수 있었습니다.
- 다양한 분봉을 지원하면서도 저장 비용과 조회 성능 사이의 균형을 맞출 수 있었습니다

## Candle 공통 인터페이스와 시간 타입 분리

### 문제
분봉, 시간봉, 일봉, 주봉 등 여러 종류의 Candle을 구현하면서 대부분의 필드와 동작이 동일하다는 것을 확인했습니다.

중복 코드를 줄이기 위해 공통 인터페이스를 도입했지만, 시간 정보를 표현하는 타입이 서로 달라 하나의 타입으로 통일하기 어려운 문제가 발생했습니다.


### 원인
분봉과 시간봉은 거래 시각까지 표현해야 하므로 LocalDateTime이 필요하지만, 일봉·주봉·월봉·연봉은 날짜 정보만 필요하기 때문에 LocalDate를 사용하는 것이 더 적합했습니다.

모든 Candle을 하나의 시간 타입으로 통일하려고 하면 불필요한 정보가 저장되거나 타입 불일치 문제가 발생했습니다.

### 해결

공통으로 사용할 수 있는 필드와 동작만 인터페이스로 추상화하고, 시간 타입은 각 Candle이 필요한 형태를 그대로 유지하도록 설계했습니다.

공통성을 유지하면서도 각 Candle의 특성을 살릴 수 있는 방향을 선택했습니다.

## 현재 Candle과 완료 Candle 저장 구조 분리

### 문제

현재 진행 중인 Candle은 체결이 발생할 때마다 시가, 고가, 저가, 종가, 거래량 등이 계속 변경됩니다.

이를 체결이 발생할 때마다 데이터베이스에 저장하거나 수정하면 불필요한 쓰기 작업이 반복되고, 실시간 처리 성능에도 영향을 줄 수 있었습니다.

또한 당일 일봉은 아직 완료되지 않았기 때문에 조회 시 매번 1분봉을 모두 계산해야 하는 문제도 있었습니다.

### 해결

현재 진행 중인 Candle은 Redis에서 관리하고, 시간이 지나 봉이 완성되는 시점에만 데이터베이스에 저장하도록 역할을 분리했습니다.

당일 일봉 역시 Redis에서 함께 관리하여 별도로 1분봉 전체를 조회하지 않아도 최신 값을 바로 조회할 수 있도록 설계했습니다.

이를 활용해 주봉, 월봉, 연봉도 당일 일봉 값을 기준으로 현재 고가와 저가를 계산하도록 구성했습니다.

### 결과

- 실시간 Candle 갱신 속도를 높일 수 있었습니다.
- 데이터베이스의 불필요한 쓰기 작업을 줄일 수 있었습니다.
- 현재 진행 중인 Candle과 완료된 Candle의 역할을 명확하게 분리할 수 있었습니다.

## Cache와 DB 조회 구간 중복

### 문제

최근 Candle 데이터는 Cache에 저장하고, 오래된 데이터는 데이터베이스에서 조회하도록 구성했습니다.

하지만 조회 범위가 Cache와 데이터베이스 구간을 동시에 포함하는 경우, Cache 데이터만 조회하면 일부 데이터가 누락되고, 두 데이터를 단순히 합치면 중복되는 문제가 발생했습니다.

### 해결

조회 요청이 들어오면 먼저 Cache와 데이터베이스의 조회 구간이 겹치는지 확인하도록 구현했습니다.

구간이 겹치는 경우에는 Cache와 DB를 단순히 병합하지 않고, 데이터 누락이 발생하지 않도록 데이터베이스를 기준으로 조회하도록 변경했습니다.

### 결과

- Cache와 데이터베이스를 함께 사용하는 환경에서도 데이터 누락을 방지할 수 있었습니다.
- 조회 결과의 일관성을 유지할 수 있었습니다.
- Cache와 DB를 혼합 사용하는 구조에서도 안정적으로 Candle 데이터를 제공할 수 있었습니다.

### 주문 수정 시 체결 후 정산 미반영 문제

## 문제

주문 수정 후 반대 호가와 즉시 체결되는 경우, TradeHistory에는 체결 내역이 정상적으로 저장되었지만 주문이 완료 처리되지 않고 보유 주식과 자산도 갱신되지 않는 문제가 발생했습니다.

특히 수정된 주문의 remainingQuantity가 0이 되어도 주문이 대기 목록에 남아 있었으며, 체결 내역만 저장되고 이후 정산 로직이 수행되지 않았습니다.

## 해결

주문 수정 전용 저장 로직(saveEditOrders)을 확인한 결과, 완료 주문을 처리하는 과정에서 일반 사용자와 봇 주문을 구분하는 필터 조건이 잘못 작성되어 있었습니다.

기존에는 OR(||) 조건으로 인해 봇 주문까지 완료 주문 처리 대상에 포함되었고, 이 과정에서 후속 로직이 정상적으로 수행되지 않았습니다.

필터 조건을 일반 사용자 주문만 처리하도록 수정하고, 삭제 대상 역시 실제 사용자 주문만 처리하도록 변경했습니다.

또한 주문 수정 과정 전체를 하나의 트랜잭션으로 처리하도록 @Transactional을 적용하여 저장과 정산이 하나의 작업으로 수행되도록 개선했습니다.

## 결과
주문 수정 후 즉시 체결되는 경우에도 주문이 정상적으로 완료 처리되도록 개선했습니다.
TradeHistory, 보유 주식, 자산 정보가 모두 정상적으로 반영되도록 수정했습니다.
주문 수정과 일반 주문의 처리 흐름을 동일하게 유지하여 데이터 일관성을 확보할 수 있었습니다.



## 주봉·월봉·연봉 실시간 캔들 병합 오류

### 문제

주봉, 월봉, 연봉으로 초기 차트를 조회할 때 당일 Redis 캔들이 새로운 봉으로 표시되지 않고, 이전 데이터베이스 캔들에 합쳐지는 문제가 발생했습니다.

예를 들어 마지막 월봉이 6월 데이터이고 Redis에는 7월 당일 데이터가 존재해도, 7월 월봉이 새로 생성되지 않고 6월 월봉에 병합되었습니다.

### 원인

`mergeLiveCandle()`에서 주봉, 월봉, 연봉의 경우 마지막 데이터베이스 캔들과 Redis 실시간 캔들이 같은 기간인지 확인하지 않고 무조건 병합하고 있었습니다.

```java
if (type == CandleType.WEEK
        || type == CandleType.MONTH
        || type == CandleType.YEAR) {

    mergeInto(lastCandle, liveCandle);
    wrappedCache.remove(wrappedCache.size() - 1);
    return;
}
```

이 구조에서는 새로운 주, 월, 연도가 시작되어도 Redis 당일 캔들이 이전 기간의 캔들에 합쳐지고, 이후 리스트에서 제거되기 때문에 새로운 캔들이 누락되었습니다.

### 해결

마지막 데이터베이스 캔들과 Redis 실시간 캔들의 기간 시작일을 계산한 뒤, 같은 기간일 때만 병합하도록 수정했습니다.

서로 다른 기간이면 Redis 실시간 캔들을 새로운 주봉, 월봉, 연봉으로 유지하도록 처리했습니다.

```java
if (type == CandleType.WEEK
        || type == CandleType.MONTH
        || type == CandleType.YEAR) {

    LocalDate lastDate =
            parseCandleTime(lastCandle.getCandleTime()).toLocalDate();

    LocalDate liveDate =
            parseCandleTime(liveCandle.getCandleTime()).toLocalDate();

    LocalDate lastPeriodStart =
            getPeriodStart(lastDate, type);

    LocalDate livePeriodStart =
            getPeriodStart(liveDate, type);

    if (lastPeriodStart.equals(livePeriodStart)) {
        mergeInto(lastCandle, liveCandle);
        wrappedCache.remove(wrappedCache.size() - 1);
    } else {
        liveCandle.setCandleTime(livePeriodStart.toString());
    }

    return;
}
```

기간별 시작일을 계산하는 공통 메서드도 추가했습니다.

```java
private LocalDate getPeriodStart(LocalDate date, CandleType type) {
    return switch (type) {
        case WEEK ->
            date.minusDays(date.getDayOfWeek().getValue() - 1L);

        case MONTH ->
            date.withDayOfMonth(1);

        case YEAR ->
            date.withDayOfYear(1);

        default -> date;
    };
}
```

### 결과

* 같은 주, 월, 연도의 Redis 당일 데이터는 기존 캔들에 정상적으로 병합됩니다.
* 새로운 주, 월, 연도가 시작되면 Redis 당일 데이터가 새로운 캔들로 생성됩니다.
* 이전 기간 캔들에 현재 기간 데이터가 잘못 합쳐지는 문제를 해결했습니다.
* 주봉, 월봉, 연봉 초기 조회 시 당일 캔들 누락을 방지할 수 있었습니다.




## 주문 수정 시 부분체결 수량 문제

### 문제

주문 수정 기능에서 부분체결이 발생한 주문을 수정할 경우,
수정 수량에 따라 이미 체결된 수량보다 적은 주문이나,
실제 남아있는 주문 수량보다 많은 주문이 생성될 수 있었습니다.

이로 인해 주문 수량과 잔여 수량의 일관성이 깨질 가능성이 있었습니다.

### 원인

기존 수정 기능은 사용자가 입력한 수량을 기준으로
주문의 총 수량과 잔여 수량을 다시 계산하도록 구현되어 있었습니다.

부분체결이 진행된 주문은 이미 일부 수량이 체결된 상태이므로,
수정 시 수량 변경까지 허용하면 주문 상태가 복잡해지고
예상하지 못한 수량이 체결될 수 있었습니다.

### 해결

주문 수정은 가격만 변경하도록 정책을 변경하고,
수량은 현재 남아있는 미체결 수량 전체만 수정 대상으로 제한했습니다.

수정 요청 시 입력한 수량과 현재 잔여 수량이 일치하는지 검증하고,
일치하지 않으면 수정을 거부하도록 구현했습니다.

이를 통해 이미 체결된 수량은 변경하지 않고,
남아있는 주문만 새로운 가격으로 다시 주문장에 등록하도록 변경했습니다.

### 결과

- 부분체결된 주문의 수량 불일치를 방지할 수 있었습니다.
- 이미 체결된 수량이 변경되는 문제를 해결했습니다.
- 주문 수정 시 가격만 변경되고 잔여 주문만 재등록되어 주문의 일관성을 유지할 수 있었습니다.


## 수정 및 미체결 주문의 기존 가격 호가 갱신 누락

### 문제

주문이 체결될 경우에는 체결 가격만 웹소켓으로 전송하고 있었습니다.

이로 인해 주문 수정이나 미체결 주문이 발생했을 때 기존 가격대의 호가 수량이 프론트엔드에 전달되지 않아, 화면에 이전 호가가 그대로 남아있는 문제가 발생했습니다.

### 원인

웹소켓으로 전달하는 가격 목록에 체결된 가격만 포함되어 있었기 때문에, 주문이 이동하면서 수량이 변경된 기존 가격대의 가격 정보는 갱신 대상에서 제외되고 있었습니다.

또한 주문 수정 시에는 기존 가격이 전달되지 않아, 프론트엔드가 이전 가격대의 호가를 갱신할 수 없었습니다.

### 해결

미체결 주문도 현재 가격의 수량을 웹소켓으로 전달하도록 수정했습니다.

또한 주문 수정 시에는 기존 주문 가격을 웹소켓 전달 대상에 추가하여, 기존 가격과 변경된 가격 모두 호가를 갱신하도록 변경했습니다.
```
if (!order.isCompleted()) {
			if (result.getExecutions().isEmpty()) {
				result.getMatchedPrices().add(order.getTradePrice());
			}
			book.addOrder(order);
		}
```
### 결과

- 주문 수정 후 기존 가격대의 호가가 정상적으로 갱신되도록 개선했습니다.
- 미체결 주문의 수량 변화도 실시간으로 프론트엔드에 반영할 수 있었습니다.

## 주문 수정 시 부분체결 수량 불일치

### 문제

부분체결된 주문을 수정하는 과정에서 주문 수량보다 많은 수량이 체결되거나, 이미 체결된 수량보다 적은 수량으로 수정되는 문제가 발생했습니다.

### 원인

주문 처리와 주문 수정 과정에서 주문장(OrderBook)에 대한 락과 데이터베이스 트랜잭션이 부분적으로만 적용되어 있었습니다.

이로 인해 주문 수정과 체결이 동시에 수행되는 경우 동일한 주문에 대해 중복으로 접근할 수 있었고, 주문의 수량과 잔여 수량이 서로 다른 시점의 데이터를 기준으로 처리되는 상태가 발생했습니다.

그 결과 주문 상태가 일관성을 유지하지 못해 예상과 다른 수량이 체결되는 문제가 발생했습니다.
